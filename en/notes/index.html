01 Workflows 6 articles 0 complete

Sequential / Prompt Chaining

↗

一次调用同时研究、起草、校验和润色，提示词会承担过多目标，任何局部错误也难以定位。Sequential 把稳定任务拆成有顺序、有契约的阶段。

planned

Routing

↗

不同请求需要不同能力与政策，却都进入同一提示词，导致上下文臃肿、答案不稳定。Routing 先判断类别，再选择有限分支。

planned

Parallelization / Fan-out Fan-in

↗

多个互不依赖的子任务串行执行会放大等待；单一回答也可能缺少多视角覆盖。Parallelization 同时运行独立工作，再合并结果。

planned

Evaluator–Optimizer

↗

一次生成很难稳定满足可明确检查的质量标准，但让生成器无限自我修改又会循环。Evaluator–Optimizer 把生成和评价分离，并设置有界反馈回路。

planned

Workflow Composition：Branch、Join、Loop 与 Fallback

↗

真实产品不是单一 pattern，而是线性步骤、条件分支、并行汇合、有界循环与降级的组合。缺少组合语义会让错误路径成为隐式代码。

planned

Workflow vs Agent

↗

Workflow 稳定但覆盖有限，Agent 灵活但不确定。团队需要基于任务证据选择，而不是把 Agent 当作默认升级方向。

planned
02 Single Agent 6 articles 0 complete

ReAct Architecture

↗

开放任务的下一步依赖工具返回，无法在运行前写成完整路径。ReAct 让模型在行动与观察之间迭代更新决策。

planned

Reason–Act–Observe Loop

↗

只画一个圆环无法实现可运营 Agent：必须明确每轮读取什么、产出什么、谁执行、状态何时提交。

planned

Reflection / Self-Critique

↗

Agent 完成后可能遗漏约束或未利用已有证据。Reflection 在最终提交前重新检查轨迹与候选结果。

planned

Critic and Revision

↗

生成者容易重复自己的盲点。独立 Critic 用不同指令、上下文或模型评价候选，再由 Reviser 定向修改。

planned

Tool-Using Agent as an Architecture Boundary

↗

模型能提出行动意图，但不能成为执行权限本身。若工具只是任意函数入口，Prompt 注入和参数错误会直接变成外部副作用。

planned

Termination、Clarification 与 Budget

↗

Agent 不知道何时停，就会过早回答、反复搜索或在信息不足时猜测。停止是一等架构能力，不是 Prompt 末尾一句话。

planned
03 Planning 6 articles 0 complete

Plan-and-Execute

↗

ReAct 一步一决策容易局部贪心，用户也难以预判长任务范围。Plan-and-Execute 先形成显式步骤，再按计划执行。

planned

Planner–Executor

↗

同一模型一边规划一边执行会混淆全局目标与局部工具细节。角色分离让计划可校验、执行可替换。

planned

Planner–Executor–Replanner

↗

静态计划遇到新证据、工具失败或目标变化后会失效。Replanner 根据已完成事实更新剩余工作。

planned

Task Decomposition and Dependency Graph

↗

任务列表只表达顺序，无法说明哪些工作可并行、哪些结果阻塞后续，也无法可靠传播取消。

planned

Plan Selection and Validation

↗

Planner 给出的第一份计划可能不可执行、过贵或忽略关键约束。执行前需要硬校验，必要时比较候选。

planned

Progress Ledger and Replanning

↗

消息历史无法可靠回答完成了什么、产物在哪里、还剩多少工作。长任务需要独立于对话的进度账本。

planned
04 Context 6 articles 0 complete

Context Engineering for Agent Systems

↗

模型不是缺少所有信息，而是缺少当前决策所需的正确信息。把全部历史塞入上下文会引入噪声、泄漏和成本。

planned

Context Selection and Progressive Disclosure

↗

一次给出所有工具说明、文档和历史会稀释当前目标。Progressive Disclosure 按需逐层开放。

planned

Context Passing between Components

↗

组件直接转发整段对话会传播噪声和隐私，也让接收者不知道什么是要求、证据或猜测。

planned

Context Isolation

↗

多 Agent 共享全部历史会造成角色干扰、敏感数据横向扩散和上下文竞争。

planned

Context Compression and Summarization

↗

长任务轨迹不断增长，成本上升且早期约束可能被挤出。Compression 将历史转成可继续工作的紧凑状态。

planned

Context Provenance and Access Boundary

↗

Agent 看到一段内容却不知道来源、时间、所有者和可信度，既无法引用，也无法正确执行权限与注入防护。

planned
05 Memory 7 articles 0 complete

Working Memory

↗

当前任务的计划、最近观察与临时变量需要跨步骤保留，但不应永久记住。

planned

Episodic Memory

↗

Agent 需要利用过去任务经验，却不能把每次对话都当永久事实。

planned

Semantic Memory

↗

跨任务稳定事实与偏好需要被检索，但来源和有效期必须清楚。

planned

Procedural / Skill Memory

↗

系统需要复用成功做法，但不能让一次偶然轨迹自动变成高权限流程。

planned

Shared vs Private Memory

↗

多 Agent 需要共享成果，但全局共享会泄漏数据并造成角色互相污染。

planned

Memory Retrieval、Write Policy and Forgetting

↗

记忆价值取决于何时读、什么能写、何时忘，而不取决于存储量。

planned

Artifact / Workspace as Memory

↗

长任务的大文件和中间成果不适合反复塞进消息，也不应被自由摘要替代。

06 Multi-Agent Fundamentals 6 articles 0 complete

Why Multi-Agent?

↗

单 Agent 在工具过多、上下文过长、专业目标冲突或独立子任务较多时会成为瓶颈，但拆 Agent 本身并不创造价值。

planned

When Not to Use Multi-Agent

↗

Multi-Agent 容易在 Demo 中显得聪明，却可能把一个 Prompt 问题放大成分布式协调问题。

planned

Single Agent vs Modular Single Agent vs Multi-Agent

↗

工具函数、Prompt 模块和独立 Agent 常被混为一谈，导致系统宣称 Multi-Agent 却没有真实决策边界。

planned

Agent Specialization and Role Boundary

↗

角色只写成“你是专家”无法建立可靠分工，容易角色漂移、工具越权和重复劳动。

planned

Final Answer Ownership

↗

多个 Agent 都能输出时，用户会收到重复、矛盾或无人负责的答案。必须有唯一可解释的最终答案所有权。

planned

Context、Cost and Failure Radius

↗

Multi-Agent 可能节省单个上下文，却增加重复前缀、通信和合成；一个错误委派还会沿链级联。

planned

Subagents / Agents as Tools

↗

主 Agent 需要专业帮助，但仍需保持用户关系、全局目标和最终答案控制权。

planned

Supervisor / Manager

↗

多个 Specialist 需要统一分解、委派、预算、合成和停止，否则会重复工作或无人负责。

planned

Router and Parallel Specialists

↗

planned

↗

某些 Specialist 需要直接与用户连续交流；Manager 代传每句话会损失细节、增加延迟和上下文。

planned

Round Robin and Selector Group Chat

↗

一些任务需要多个角色基于彼此结果迭代，而不是独立返回一次；需要定义谁下一位发言。

planned

Swarm

↗

中心 Supervisor 可能成为瓶颈；在角色网络中，当前 Agent 可更快判断应该把控制交给哪个邻居。

planned

Hybrid Multi-Agent Patterns

↗

真实产品常同时需要入口路由、后台专业计算、直接 Handoff 和质量评价，单一 Pattern 无法覆盖。

planned

↗

AI 应用需要以统一方式发现和调用外部工具、资源与提示，同时让应用保留上下文、同意和安全控制。

↗

14 Reliability 8 articles 8 complete

Agent Failure Taxonomy

↗

Agent 失败不只有答案错误，还包括决策、工具、状态、通信、权限、运行时和产品承诺失败。

complete

Retry and Fallback

↗

瞬时故障可重试，但语义错误和副作用盲重试会放大损害。

complete

Timeout and Cancellation

↗

没有 deadline 的 Agent 会无限等待；取消不传播则后台仍消耗和执行。

complete

Termination and Loop Detection

↗

Agent 可能重复行动、角色互相交接或计划震荡，max_steps 只能限制损失不能识别原因。

complete

Idempotency and Side-Effect Safety

↗

重试、恢复和重复消息可能让发送、扣款、删除执行多次。

complete

Partial Failure and Compensation

↗

并行或多 Agent 系统中部分成功是常态，整单回滚常不可行。

complete

Multi-Agent Failure Modes

↗

多个 Agent 新增角色漂移、错误委派、上下文丢失、冲突、群体偏差、级联错误和通信爆炸。

complete

Recovery、Checkpoint and Resume

如何公平比较 Agent 框架

↗

框架选择首先是架构选择。相同的“支持多 Agent”，可能分别意味着图节点、角色团队、工具调用或控制权移交，产品的可控性与故障形态完全不同。

complete

LangGraph：把 Agent 建模为有状态图

↗

LangGraph 的核心不是“很多 Agent”，而是持久化的 StateGraph：节点读取和更新状态，边决定下一步。显式控制流、检查点和可恢复执行适合长任务、审批与复杂分支。

complete

AutoGen 与 Microsoft Agent Framework：从对话协作到企业工作流

↗

AutoGen 让“会话中的多个角色”成为易理解的协作模型，团队、选择器、群聊和消息驱动适合探索协作行为。Microsoft Agent Framework 进一步把 Agent 抽象、会话状态、中间件、遥测和图工作流放进统一的企业运行模型。

complete

CrewAI：角色团队与事件流的组合

↗

Crew 强调有目标、角色和任务分工的 Agent 团队；Flow 强调带状态、事件和分支的可控业务流程。产品级用法通常不是二选一，而是让 Flow 管住生命周期，在某个节点调用 Crew 完成开放式协作。

complete

OpenAI Agents SDK：轻量 Agent、工具与 Handoff

↗

OpenAI Agents SDK 以 Agent、tools、handoffs、guardrails、sessions 和 tracing 为核心。它不强迫使用图；团队可以让代码决定编排，也可让模型在工具调用和 Handoff 中决定下一步。

complete

Google ADK：LLM Agent 与确定性 Workflow Agent

↗

Google ADK 区分依赖模型推理的 LLM Agent 与负责确定性控制的 Workflow Agent。Sequential、Parallel、Loop 等组合原语让团队把确定流程写清，再在合适节点引入模型自主性，并可通过多 Agent 和 A2A 扩展。

complete

从产品约束选择 Agent 框架

↗

不存在总体最好的框架，只有对当前风险、团队和生命周期更合适的组合。选型顺序应是任务确定性→持久化与审批→协作形态→生态与团队能力→退出成本，而不是先挑框架再迁就产品。

complete

同一系统的多框架架构映射

↗

框架不同，但稳定的产品架构概念应能互相映射：任务状态、阶段、角色、工具、Handoff、审批、恢复和观测。如果系统只能用某个类名解释，通常还没有形成清晰架构。

complete
17 Real System 10 articles 10 complete

版本 1：从确定性工作流开始

↗

第一版不需要自主 Agent。用户真正要的是一份结构完整、来源可追踪、按时返回的报告；固定流程已经能验证需求、数据源和质量标准，也提供以后比较的基线。

complete

版本 2：Router、Parallel 与 Evaluator

↗

基线暴露三个瓶颈：不同报告类型需要不同模板，独立来源串行检索太慢，草稿质量只能人工发现。Router、Parallel 和 Evaluator 分别解决适配、时延和质量反馈，不需要开放式 Agent 循环。

complete

版本 3：在受限范围内引入 ReAct Agent

↗

部分研究问题需要根据刚发现的信息继续选择查询、打开文件或补证据，固定检索分支会不断膨胀。版本 3 只把“探索研究”阶段替换为一个 ReAct Agent，其余流程、质量门和发布仍保持确定性。

complete

版本 4：Planner–Executor–Replanner

↗

当报告跨多个公司、地区和时间段时，单个 ReAct Agent 容易局部探索过深、遗漏任务或重复劳动。Planner 提供全局任务图，Executor 完成原子任务，Replanner 只根据新证据修订未完成部分。

complete

版本 5：上下文隔离与分层记忆

↗

随着计划和工具轨迹增长，模型会被无关内容干扰；重复客户研究又在浪费已验证事实。版本 5 把上下文选择、短期任务状态、长期知识和最终产物分开治理。

complete

版本 6：Supervisor 与 Specialist Agents

↗

当研究、数据分析、风险判断和编辑需要不同工具、提示、权限与评估标准时，单 Agent 的上下文和权限过宽。Supervisor 负责分解、委派、合并和预算，Specialist 只完成边界清晰的专业任务。

complete

版本 7：Handoff 与层级团队

↗

有些任务不是“主 Agent 调专家再回答”，而是用户需要与合规或行业专家持续澄清；同时专家数量增加后，单一 Supervisor 成为瓶颈。Handoff 解决会话所有权转移，层级团队解决管理跨度。

complete

版本 8：用状态图统一复杂编排

↗

到版本 7，路由、规划、专家团队、质量返工和人工批准已经形成复杂生命周期。继续散落在回调和提示词中会难以理解与恢复，因此用状态图统一业务阶段，而不是把所有 Agent 行为改写成图。

complete

版本 9：MCP 工具与 A2A 远程 Agent

↗

当数据工具由不同团队维护、某些专家由外部服务提供时，进程内函数和本地子 Agent 不再够用。MCP 统一 Agent 对工具与资源的访问，A2A 统一 Agent 对远程 Agent 任务与产物的协作，两者解决不同边界。

complete

版本 10：可靠性、HITL、可观测与评估闭环

↗

最终升级不是再增加一个 Agent，而是让整个系统在真实故障、敏感操作和模型变化中仍兑现产品承诺。可靠性处理运行错误，HITL 管理决策边界，可观测性解释发生了什么，Evals 判断系统是否真的变好。

complete
